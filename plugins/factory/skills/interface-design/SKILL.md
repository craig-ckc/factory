# Interface Design

Decide how an interface should work and communicate, not merely how it should look.

## Approach

1. Ground decisions in the problem, actors, tasks, and existing product.
2. Map the user journey, navigation, hierarchy, interaction states, and feedback.
3. Reuse the product's design system, conventions, and domain language.
4. Consider responsiveness, accessibility, error recovery, and realistic content while shaping the design. Read only relevant shared references: [layout](../../references/design/layout.md), [typography](../../references/design/typography.md), [color](../../references/design/color.md), [accessibility](../../references/design/accessibility.md), [interface writing](../../references/design/interface-writing.md), [motion](../../references/design/motion.md).
5. Collaborate with Architecture/Implementation where technical constraints affect the experience.
6. Use [Prototype](../prototype/SKILL.md) to test materially different directions when uncertain; don't generate variants by default.
7. Explain meaningful tradeoffs rather than elevating personal taste to a requirement.

## Output

A coherent interaction/design direction, states and behavior, and guidance sufficient for Interface Build.

## Finish

A user can understand the intended workflow and the rationale for key decisions.
